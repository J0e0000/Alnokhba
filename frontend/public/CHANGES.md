# النخبة — سجل التغييرات

## Round 12 — الإصلاح النهائي: الحضور بيفشل في «حصة تانية» نفس اليوم (23505)

### المشكلة (مُثبتة بالدليل على قاعدة بياناتك الحية)
بعد تطبيق Round 11، أول حصة في اليوم بتحفظ عادي — لكن **أي حصة تانية لنفس الطالب في نفس اليوم** (زر «فتح حصة جديدة» أو مجموعة تانية) بتفشل برسالة:
```
تعذر حفظ حضور [اسم الطالب] (غائب). السبب: [23505] duplicate key value
violates unique constraint "idx_attendance_records_student_day"
```
**السبب الحقيقي** (اتلمس باليد على قاعدة بياناتك): يوجد **فهرس فريد قديم** اسمه `idx_attendance_records_student_day` على الأعمدة `(student_id, attendance_date)` — يعني «سجل حضور واحد فقط للطالب في اليوم كله». المنصة بتسمح بفتح أكثر من حصة في اليوم، فأول حصة بتعدي والتانية بتضرب في الفهرس ده. ونفس الخطأ بيضرب **التحويل التلقائي للغايبين عند إنهاء الحصة** — عشان كدا الغياب كان بيرجع «لم يرصد».

### الحل (ملف SQL واحد: `migration_041_fix_student_day_index.sql`)
1. **حذف التفرّد اليومي الخاطئ** `(student_id, attendance_date)` — فهرس كان أو قيد جدول، مهما كان اسمه (بيشيل `idx_attendance_records_student_day` وأي نسخة منه).
2. **التفرّد الصح**: فهرس فريد جديد على `(lesson_session_id, student_id)` — صف واحد لكل طالب **في كل حصة** (مش في اليوم).
3. **إعادة بناء الدوال الثلاث بصيغة ذرّية ON CONFLICT**: مفيش سباق (double-tap على الزرار) ومفيش 23505 ولا صفوف مكرّرة — نهائيًا.
4. **تحسين الإنهاء**: الطالب اللي ليه واجب متسجل بس (حضوره «لم يرصد») بيتحوّل «غايب» عند الإنهاء برضه — عقد الواجهة بيطلب إن كل طلاب المجموعة يخرجوا «حاضر/غايب» بعد الحفظ (قبل كدا الحالة دي كانت بتفشّل الحفظ النهائي برسالة «لم يكتمل سجل الحضور»).
5. مفيش أي بيانات بتتمسح — تنظيف التكرارات القديمة (لو في) بيجبل الأحدث بس.

### التحقق (52/52 اختبار + تجربة حية على الموقع نفسه)
1. **تجربة حية كاملة على قاعدة بياناتك الحقيقية** (حساب تجريبي اتعمل بالفعل): دخول → إضافة طلاب → فتح حصة → **حاضر ✓ / غايب ✓ / تبديل مرتين ✓ / واجب ✓ / إنهاء ✓** — كل الكتابات وصلت قاعدة البيانات (بتواريخ فعلية) + **بوابة الطالب (student portal) استقبلت كل حاجة فورًا** (حضور/غياب/واجب/تنبيهات).
2. **إعادة إنتاج الخطأ نفسه على قاعدة مطابقة**: فهرس اليومية موجود → حصة تانية → 23505 بالظبط زي حيّك → تشغيل migration_041 → **كل الحالات عدّت**.
3. **39/39 اختبار** على PostgreSQL حقيقي: 3 حصص في نفس اليوم، تبديلات، واجب محافظ على الحضور، خصم مرة واحدة، إعادة إنهاء idempotent، صلاحيات/RLS/إشعارات.
4. **13/13 اختبار إضافي**: ضيف/مدرس غريب/حالة غير معروفة/محايد/تكرارات قديمة بتتشال وتتجدد الفهارس.
5. **آيفون (محرك Safari الحقيقي WebKit)**: تجربتين كاملين — حضور → غياب → حضور → غياب (تبديل متكرر) — **كل الضغطات وصلت قاعدة البيانات بـ timestamps فعلية** (أكثر من 10 كتابات من محرك الآيفون نفسه).
6. قبل الإصلاح: الفهرس اليومي كان مانع حتى على الكمبيوتر — يعدي **مش مشكلة آيفون**، هي مشكلة قاعدة بيانات بتظهر على كل الأجهزة.

### إزاي تشغلها (خطوة واحدة)
**شغّل `migration_041_fix_student_day_index.sql`** في Supabase ← SQL Editor ← New query ← الصق الملف كله ← Run.
- آمن لإعادة التشغيل، آمن فوق 040 وكل الميجريشنات اللي قبله، مفيش حاجة بتتمسح.
- مش محتاج ترفع واجهة جديدة — الواجهة الحالية كفاية. (لو حابب، النسخة المرفقة بتضيف شرح عربي واضح لو ظهر 23505 تاني بدل الرسالة التقنية.)

## Round 11 — إصلاح جذري لمسار حفظ الحضور (تعذر حفظ الحضور / الغياب مش بيتسجل)

### المشكلة
المدرّس بيسجل حضور/غياب الطالب فتظهر رسالة **«تعذر حفظ حضور الطالب ده حاول مرة أخرى»**، وبعد إنهاء الحصة الحضور يرجع «لم يرصد» زي لو مكانش اتعمل حاجة — يعني الكتابة نفسها واقعة على الأرض.

### التشخيص (بالدليل)
- فحصنا **قاعدة البيانات الحية** (الـ schema بتاعك) Statement بـ Statement: كل الجداول والأعمدة سليمة، وكل الدوال (RPCs) موجودة بالتوقيعات الصح — يعني المشكلة **مش في الواجهة ومش في شكل الجداول**، السبب بقى **جوه دوال الكتابة نفسها أو التريجرات** (اتأثرت مع آخر تحديثات SQL).
- عشان كده الحل كان لازم يكون **استبدال جذري لمسار الكتابة كله** بنسخة مضمونة ومختبرة — مش ترقيع لنقطة واحدة.

### الحل

**1) ملف SQL واحد: `migration_040_attendance_bulletproof.sql`** (شغّله مرة واحدة في SQL Editor — آمن للتكرار):
- **استبدال كامل** للثلاث دوال المسؤولة عن كل كتابة الحضور:
  - `upsert_lesson_attendance` — تسجيل حاضر/غائب/محايد داخل الحصة (صف واحد لكل طالب، تنظيف أي تكرار قديم، رفض الحصة المنتهية برسالة عربية واضحة).
  - `upsert_lesson_homework` — تسليم الواجب (من غير ما يلمس حالة الحضور).
  - `finalize_lesson_session` — إنهاء الحصة: الطلاب غير المرصودين بيتحولوا «غايبين» تلقائيًا + خصم النقاط مرة واحدة بس (مفيش خصم مزدوج) + إرجاع العدادات (حاضر/غايب).
- **إعادة تفعيل تريجرات الإشعارات بالنسخة الآمنة**: أي عطل في الإشعار **لن يمنع أبداً** حفظ الحضور (كان ده أخطر نقطة — التريجرات القديمة ممكن تكسر الحفظ لو جدول التنبيهات فيه مشكلة).
- **إعادة ضبط سياسات RLS** على جداول الحضور + الصلاحيات (الدوال للمدرّسين المسجلين فقط).
- مفيش أي بيانات بتتمسح — كله `create or replace` + تنظيف تكرارات.

**2) الواجهة — إظهار السبب الحقيقي في رسالة الخطأ** (`src/lib/helpers.js` + `Dashboard.jsx`):
- قبل كدا: «تعذر حفظ الحضور... حاول مرة أخرى» (من غير أي سبب).
- دلوقتي: «تعذر حفظ حضور أحمد (غائب). **السبب: [كود الخطأ] تفاصيل الخطأ**» — ولو الدالة ناقصة بيقولك نفّذ ملف الـSQL المرفق. أي مشكلة مستقبلية هتظهر فورًا بدل ما تضيع.

### التحقق (كله على قاعدة بيانات PostgreSQL حقيقية + محرك PostgREST زي Supabase بالظبط)
1. **51/51 اختبار** على PostgreSQL حقيقي ضد المايجريشن نفسه: كل الحالات (حاضر/غايب/محايد/تبديل/إعادة نفس الحالة)، الصلاحيات (المالك/المساعد/مدرس غريب/غير مسجل)، الحصة المنتهية، تنظيف التكرارات، خصم النقاط مرة واحدة، الإشعارات، سياسات RLS، وإعادة تشغيل المايجريشن idempotent.
2. **تجربة حقيقية كاملة في المتصفح** ضد بنية مطابقة للحي (PostgREST + PostgreSQL): إنشاء حساب → دخول → إضافة 3 طلاب → فتح حصة → تسجيل حاضر/غايب → إنهاء الحصة → التأكد إن **الغياب اتحفظ والنقاط اتخصمت مرة واحدة والإشعارات وصلت** — 0 أخطاء.
3. **آيفون (محرك Safari الحقيقي — WebKit)**: نفس خطوات الحضور اتعملت من المتصفح بتاع Safari نفسه (حضور ثم غياب) — **اتحفظوا في قاعدة البيانات بضمان timestamp** — 0 أخطاء.
4. **اختبار الكسر والإصلاح**: تم تعطيل الدالة عمدًا → ظهرت رسالة الخطأ بالسبب الحقيقي `[P0001] فشل داخلي تجريبي 555` → إعادة تشغيل المايجريشن → الحفظ رجع شغال فورًا.
5. run-all.sh **8/8** (186+ فحص) ✓ — npm run build ✓.

### إزاي تشغلها
1. **شغّل `migration_040_attendance_bulletproof.sql`** في Supabase ← SQL Editor ← Run. (الرقم مش مهم — آمن فوق أي ميجريشن شغالته قبل كدا، وآمن لإعادة التشغيل).
2. انسخ ملفات الواجهة المحدثة (أو الـ zip كله) وادعم النسخة الجديدة.
3. جرّب من الآيفون: افتح حصة → سجّل غياب → هتلاقيه اتحفظ على طول + الطالب في البوابة شايفه.

## Round 8 — تعديل درجات الامتحانات (عمليتان منفصلتان)

### إيه اللي بقى موجود
كل امتحان دلوقتي ليه **زرين تعديل مختلفين تمامًا** — كل واحد بصلاحية وسجل تدقيق مستقل:

**A) ✏️ تعديل الدرجة العظمى للامتحان (كل الامتحانات ← ✏️ تعديل العظمى)**
- بتغير الدرجة العظمى الكلية (مثال: 40 → 50) — والنظام بيظبط «لكل قسم» تلقائيًا (10 لكل قسم).
- **درجات الطلاب المسجلة مبتتغيرش خالص**: الطالب اللي 32/40 يفضل 32/50 — بس النسبة والدرجة النهائية بتتحسب من العظمى الجديدة.
- حماية تاريخية: لو فيه درجة طالب أعلى من العظمى الجديدة → التعديل بيرفض برسالة عربية واضحة.
- لازم العظمى تقبل القسمة على عدد الأقسام (50 على 5 = 10 ✓) — الواجهة بتقترحلك أقرب رقم صحيح.

**B) ✏️ تعديل درجة طالب واحد (كل الامتحانات ← 📋 الدرجات ← ✏️)**
- بتغير درجة طالب واحد بس — **الباقي مبيتأثروش والدرجة العظمى مبتتغيرش**.
- درجة الطالب بتتحدث في نفس مكانها (inline) من غير أي شاشة حاجزة — والواجهة بتتحدث فورًا من رد السيرفر (من غير reload).
- الأقسام بتتوزع نسبيًا على الدرجة الجديدة عشان التقارير تفضل متسقة (مجموع الأقسام = المجموع الجديد).
- نقاط الطالب بتتظبط بنفس معادلة الرصد الأصلية بالظبط (الفرق فوق/تحت نصف العظمى) — والفرق بيظهر في الـ toast (+3 نقطة مثلاً).

## Round 7 — تزامن لحظي + ضمان واتساب على أندرويد وآيفون

### 1) كل البيانات بتتحدث لحظيًا (المدرس)
- **كان المشكلة:** قناة Realtime القديمة كانت مسجلة على 3 جداول بس (students / behavior_logs / session_logs). أي تغيير في **الحصص (lesson_sessions)** أو **الحضور (attendance_records)** أو **الدرجات (exam_scores)** أو **الجدول (group_schedule)** أو **الإعدادات (teacher_settings)** أو **الرسائل العامة** ما كانش بيظهر غير بعد refresh كامل — وده بالظبط «السجل مش متزامن مع الحصص».
- **الحل:** نفس القناة دلوقتي مسجلة على كل الجداول التسعة. أي تغيير (من الجهاز ده أو من جهاز تاني أو من طابور الـ offline بعد رجوع النت) يحدّث الواجهة فورًا:
  - **الحصص:** فتح/تعديل/إنهاء/حذف درس يظهر لحظيًا، ولو درس اتفتح من جهاز تاني وهو مكتوب اسم مجموعته دلوقتي بيتadopted تلقائيًا (من غير ما يمسح اللي المدرس بيكيبه — حارس sessionHasChanges شغال).
  - **الحضور:** أي رصد (حاضر/غائب/واجب) يعدّل خريطة الحصة النشطة فورًا + يعيد حساب سلسلة الغياب المتتالية للطالب (استعلام مصغّر debounced).
  - **الدرجات:** النتائج الجديدة تظهر في الرسوم والتحذير الأكاديمي بدون reload.
  - **الإعدادات/الجدول:** تعديل مجموعة أو إعدادات من جهاز تاني ينزل فورًا + «مجموعات النهارده» بتتحدث لو اليوم انقلب والصفحة مفتوحة.
  - **دفتر اليوم (session_logs):** حماية من الكتابة القديمة اللي كانت بتطغى على سجل اليوم + دعم الحذف.
- **سجل حصص المجموعة (SessionHistoryModal):** بقى بيحدث نفسه لحظيًا وهو مفتوح — إنهاء حصة من أي جهاز يظهر فيه فورًا.

### 2) بوابة الطالب بتتحدث لحظيًا
- **كان:** بوابة الطالب (/qr/:token) بتعمل polling كل 10 ثواني بس.
- **الحل (portalRealtime.js):** قناة broadcast خفيفة `portal-refresh-<teacherId>`:
  - لوحة المدرس بتطلع «ping» (بدون أي بيانات طالب — مصدر + وقت بس) لحظة أي تغيير في أي جدول.
  - كل بوابة طالب مفتوحة بتسمع الـ ping ده وبتعمل refresh فوري (debounce 450ms + حماية من التكرار).
  - لو الطالب رجع للتاب/الأب بعد ما ضغط home — الصفحة بتتحدث فورًا (visibilitychange) — قبل كده الموبايل كان بيجمّد المؤقت والصفحة تفضل قديمة.
  - الـ polling كل 10 ثواني فضل كشكول أمان لأي مصدر تغيير تاني.
  - **الأمان:** الـ ping نفسه مفيهوش أي بيانات؛ البيانات بتيجي من نفس الـ RPC المؤمّن بالـ token — الـ ping بيقول «حدّث نفسك» بس.
- **لوحة الإعلانات:** بعد إرسال/حذف إعلان، كل البوابات المفتوحة بتشوفه خلال ثانية.

### 3) ضمان تقارير واتساب على أندرويد وآيفون (تحسين Round 4)
- كل مسارات الإرسال اتختبرت live على متصفح بمحاكاة iPhone 14 (window.open ممنوع — نفس سلوك iOS بعد async):
  - **الرسالة الفردية / التقرير الكامل / رسائل الإنذار والترقية:** بيوصلوا لواتساب (wa.me → التطبيق على الموبايل).
  - **شريط «فتح واتساب»:** ظاهر، لينك حقيقي `<a target="_blank">` — المسار المضمون على آيفون.
  - **طابور الرسائل:** أزرار `<a>` حقيقية زي ما هي.
- **الجديد — رسائل صادقة:** قبل كده لو آيفون حجب الفتح التلقائي، التطبيق كان بيكتب «تم الإرسال» رغم إن مفيش حاجة اتفتحت. دلوقتي `lastWhatsAppHandoffInfo()` بيقول للمدرس: «التقرير جاهز — لو واتساب ما اتفتحش لوحده، اضغط زر «فتح واتساب» اللي ظهر تحت» — على آيفون بس؛ أندرويد/الكمبيوتر بيكملوا «تم الإرسال» عادي لأن الفتح التلقائي بيشتغل عندهم فعلاً.
- إصلاح في وحدة البث: طبقات البينجات المتتالية في نفس المللي ثانية ما بقتش بتتلغي (كانت بتتشال كـ «مكررة» بالغلط).
